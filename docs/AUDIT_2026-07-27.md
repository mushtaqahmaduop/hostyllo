## Verdict

The API is materially healthier than at the ARB audit five days ago. Tenant isolation is now
enforced by the database rather than by convention, and it is covered by CI. Nothing found here is
a tenant-isolation hole.

What this audit *did* find is a different class of problem: **the production database is not a
database anyone can safely migrate**, and **the app runs an end-of-life web framework**. Both are
fine today, with 2 users and 1 test student. Neither is fine with paying customers on it.

## 1 · Tenant boundary — CLEAN

64 endpoints across 16 route modules. Every route-level DB call now goes through `withTenant()`,
which connects as the RLS-bound `hostyllo_app` role, and that is mechanically enforced as of
2026-07-27 (see PR #29 — the ESLint plugin had never actually been loaded).

Verified live, read-only:

| | Production `eprrhckgtrerknenngdy` | Staging `ljnuwmfnpofzlmioskfc` |
|---|---|---|
| public tables | 28 | 29 (incl. `schema_migrations`) |
| RLS **enabled** | 28 / 28 | 28 / 28 |
| RLS **forced** | 28 / 28 | 28 / 28 |

FORCE is the part that matters: with ENABLE alone the table owner bypasses RLS, which is what made
the pre-migration-010 policies decorative. A forgotten `hostel_id` filter now returns 0 rows rather
than another tenant's data — fail-closed.

`no-hostel-id-from-request` reports zero violations across all 16 modules, and that result is now
meaningful: the rule previously only matched an identifier named `req`, while every route in the
codebase names it `request`.

**Residual gap (🟡):** `isolation.test.ts` proves cross-tenant 404s for students, rooms and
payments — **3 of 16 route modules**. The PRD gate says *every* endpoint. FORCE RLS makes a leak
unlikely, but "unlikely" is what the gate exists to eliminate. A table-driven test that walks every
registered route and asserts A's token → B's id is 404 would close it in about half a day.

## 2 · 🔴 Production has no migration ledger, and its schema differs from staging

The M3 migration runner (`packages/db/migrate.mjs`) and its `schema_migrations` ledger exist and
work. Staging uses them: all 11 migrations are recorded, applied 2026-07-22.

**Production has no `schema_migrations` table at all.** `to_regclass('public.schema_migrations')`
returns NULL. Prod was migrated by hand and through MCP calls, and was never baselined.

Two consequences, both real:

1. **Nothing knows what prod has.** Running `migrate.mjs up` against production today would try to
   apply 001–011 from scratch against a schema that already has them.
2. **Staging is not a faithful rehearsal of production.** Concrete evidence — the `users` table:

   | | production | staging |
   |---|---|---|
   | `totp_secret` | **present** (legacy plaintext, 0 rows populated) | absent |
   | `totp_secret_enc` | present | present |

   Migration 009 *renames* `totp_secret` → `totp_secret_enc`. Staging, built by the runner, shows
   the renamed result. Production, hand-migrated, kept both. A migration that passes on staging can
   therefore still fail on production.

**Fix — founder decision required, two steps, neither destructive:**

```bash
# 1. Record what prod already has, executing no SQL:
DATABASE_URL='<prod>' node packages/db/migrate.mjs baseline

# 2. Then drop the legacy column (verified empty: 0 of 2 users have a value):
#    ALTER TABLE public.users DROP COLUMN totp_secret;
```

I did not run either. Step 1 creates a table on production; step 2 drops a column. Both are writes
to the live database and are yours to authorise. Step 2 is safe *now* precisely because prod holds
no real data — that window closes with the first customer.

## 3 · 🔴 Fastify 4 is end-of-life; every runtime CVE traces to it — ✅ RESOLVED 2026-07-27

> **Update (same day, PR #31):** upgraded to **Fastify 5.10.0** with `@fastify/cors` 11,
> `@fastify/helmet` 13, `@fastify/cookie` 11, `@fastify/multipart` 10 (which also retires the
> v10→v8 downgrade this section flagged). One code change was needed: Fastify 5 widened
> `setErrorHandler`'s error parameter to `unknown`, so it is annotated `FastifyError` explicitly.
> A `fast-uri: ">=3.1.4"` pnpm override clears the last transitive advisory.
>
> **Result: 42 → 26 findings, and zero runtime high/critical remain.** Everything still reported
> is dev tooling (`vitest`/`vite`/`postcss`) or build-time (`tar`, `brace-expansion` via bcrypt's
> `node-pre-gyp`). `engines.node: ">=20"` added at the root — CI pins 22, but Railway's builder
> chooses the runtime itself and nothing told it a minimum.
>
> The original finding is preserved below as written.

`pnpm audit` before this pass: **42 vulnerabilities, 5 critical**. After removing three dead
dependencies (§4): **36, 2 critical** — and both remaining criticals are non-runtime (`vitest`, a
devDependency; `tar`, pulled in by bcrypt's build-time `node-pre-gyp`).

Every remaining **runtime** high traces to one root: `fastify@4.29.1`.

| Advisory | Package | Patched in |
|---|---|---|
| Content-Type tab character allows body validation bypass | fastify | ≥ 5.7.2 |
| `request.protocol`/`host` spoofable via `X-Forwarded-*` | fastify | ≥ 5.8.3 |
| DDoS with HTTP/2 | find-my-way (Fastify's router) | ≥ 9.7.0 |
| Host confusion via percent-encoded / backslash authority delimiters | fast-uri (via Fastify's ajv) | ≥ 3.1.4 |

**There is no fix on the 4.x line — the patched versions are all 5.x.** This also blocks a known
piece of debt: `@fastify/multipart` was pinned back v10 → v8 because v10 requires Fastify 5.

**Recommendation:** schedule a Fastify 4 → 5 upgrade as the first infrastructure task of Phase 2,
before the frontend starts depending on API behaviour. It is a breaking-change upgrade across 16
route modules and 64 endpoints; the integration suite (40 tests) is the safety net that makes it
tractable. Not attempted here — it is not an audit-sized change.

## 4 · 🟠 Three dependencies were dead and carried 3 CRITICAL CVEs — REMOVED

`@fastify/jwt` was declared as a dependency and **never imported or registered**. All JWT work goes
through `jose` in `lib/jwt.ts`. It dragged in `fast-jwt`, the source of three criticals — including
*"Cache Confusion via cacheKeyBuilder Collisions Can Return Claims From a Different Token"*, which
in a multi-tenant app is precisely the failure mode this whole architecture exists to prevent. It
was never reachable, because the library was never called, but it sat in the lockfile looking like
an authentication dependency.

Also removed: `@fastify/rate-limit` (0 uses — `auth.ts` hand-rolls Redis rate limiting) and
`@otplib/preset-default` (0 uses — `otplib` v13 is used directly).

Verified after removal: `buildApp()` constructs and `ready()` resolves; workspace builds; lint and
typecheck clean.

## 5 · 🟠 The DLQ recorded jobs that were not dead — FIXED

`docs/06_CLAUDE_MD_v15.md` has documented the correct pattern all along:

```ts
worker.on('failed', async (job, err) => {
  if (job && job.attemptsMade >= (job.opts.attempts ?? 3)) await moveToDLQ(job, err);
});
```

All five workers instead called `moveToDLQ(job, err)` unconditionally. BullMQ emits `failed` on
**every attempt**, so a job configured for 5 attempts that failed four times and then succeeded
wrote four rows into `dlq_jobs`. An operator reading the dead-letter table would see dead jobs that
had in fact completed — and would have no way to tell which.

Fixed inside `moveToDLQ` rather than in five separate handlers, so there is one definition of
"exhausted". Covered by a new test that asserts a job on attempt 1 of 3 is *not* recorded and the
same job on attempt 3 *is*.

**Note on the gate wording:** the PRD's "DLQ confirmed on all 7 queues" is unsatisfiable in
Phase 1. The 7 in `06_CLAUDE_MD_v15.md` includes `whatsapp-blast` and `whatsapp-receipt`, which are
unbuilt Phase-2 features. The repo has 5 workers and all 5 call `moveToDLQ`. The gate should say 5,
with the WhatsApp queues moved to the Phase-2 list.

## 6 · 🟠 The authorization matrix is incoherent

`requireRole()` accepts both `requireRole(['a','b'])` and `requireRole('a','b')` (it flattens), so
the two calling styles in the codebase are not a bug. The **policy** is.

`students.ts` grants `chain_manager` the two most sensitive operations while denying it the
ordinary ones:

| Endpoint | warden | hostel_owner | chain_manager |
|---|:--:|:--:|:--:|
| `GET /students` (list) | ✅ | ✅ | ❌ |
| `GET /students/:id` | ✅ | ✅ | ❌ |
| `POST /students` | ✅ | ✅ | ❌ |
| `PATCH /students/:id` | ✅ | ✅ | ❌ |
| `DELETE /students/:id` | ❌ | ✅ | ❌ |
| **`GET /students/:id/reveal-cnic`** | ❌ | ✅ | **✅** |
| **`POST /students/import`** (bulk) | ✅ | ✅ | **✅** |

A chain manager cannot read a student record, but can reveal that student's national identity
number and bulk-import students. Every other module grants `chain_manager` alongside
`hostel_owner` consistently. This reads as drift, not design.

**Second finding:** the `users.role` CHECK constraint permits four roles —
`hostel_owner`, `chain_manager`, `warden`, `viewer` — but **`viewer` appears in zero `requireRole`
calls across all 64 endpoints**. A user created with that role can log in and receives 403 from
every endpoint in the product.

**Both need your decision, not my guess:** should `chain_manager` have full student access, and is
`viewer` a real read-only role (add it to the GET guards) or dead (drop it from the constraint)?
